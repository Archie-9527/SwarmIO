# SwarmIO + BaM 研究路线与版本约定

确定日期：2026-11-10。本文记录已确定的开发范围、版本依赖及实验验收规则，不表示尚未实现的功能已经可用。

## 1. 总体路线

| 阶段 | 工作 | 归属及依赖 |
|---|---|---|
| 1 | 多 CPU、多 GPU、多 DSA 适配，提高双 socket 服务器可达 IOPS | SwarmIO/BaM V1，从 V0 发布分支开发 |
| 2 | SQE 发起与 CQE 轮询分离，通过状态表同步完成，支持计算/I/O 重叠 | SwarmIO/BaM V2，从 V1 发布分支开发 |
| 3 | KV offload 中间层及推理引擎对接 | 独立应用适配工程，使用 V2 的请求接口 |
| 4 | 简单 FTL：状态、GC、磨损分布、耐久预算及写放大 | SwarmIO V3，从 V2 发布分支开发；可与阶段 3 并行 |
| 5 | KV offload 测试分析 | 独立应用工程；固定推理引擎、中间层与框架版本 |
| 6 | 磁盘向量检索测试分析 | 独立应用工程；具体系统和接入层到该阶段再确定 |

阶段 3、5、6 的推理引擎、模型、检索系统和完整中间层不并入 SwarmIO。框架只提供所需的通用请求、完成、数据装载及统计能力；应用相关语义留在适配层。

## 2. 当前基线 V0

- 发布分支：`release/v0-single-dsa`。
- SwarmIO 源码锚点：`2d9baa8ccee73868a14bc4c20fe044a5a6ff8e56`。
- BaM gitlink：`bd9141524f23a179e8b1719cabcefb42e500a7bf`。
- 后端：DSA 合并获取 GPU SQE、异步硬件 BATCH 搬运 payload、CPU 写 CQE。
- GPU 提交协议：每线程发起请求后等待该请求完成，再继续下一次请求。
- 已有实验：单 dsa0、GPU0 的 512B 随机 READ 达到约 12M IOPS。
- 现有限制：单设备入口；异步 payload 请求限制在单 4KiB 缓冲区页内；DSA 基准只产生 READ；尚无 FTL。

这里的“DSA 异步 BATCH”是已有后端搬运机制；V2 的“异步重叠”是前端请求接口及完成处理分离，两者不得混称为同一项新增优化。

基线重现说明见 [V0](releases/v0-single-dsa.zh-CN.md)，机器可读记录及两次历史运行副本见 `experiments/baseline-v0/`。当前提交是后续源码比较锚点，不冒充历史构建 manifest 中已经证明的源码版本。

## 3. 发布链与分支规则

```text
release/v0-single-dsa
  └─ dev/v1-numa
       └─ release/v1-numa          （V1 服务器验收后建立）
            └─ dev/v2-async
                 └─ release/v2-async    （V2 服务器验收后建立）
                      └─ dev/v3-ftl
                           └─ release/v3-ftl （V3 服务器验收后建立）
```

1. 下一版本从上一版本已验收的发布分支建立，记录确切父提交；不提前把未实现版本命名为已发布版本。
2. 每个版本在本版本内部开发、构建、测试，保留其配置、测试脚本、文档和依赖清单。
3. 发布时使用不可变的版本 tag 固定测试快照；发布分支如有修复，另建 patch tag，已有结果仍引用原 tag/提交。
4. BaM 是独立仓库。涉及 BaM 时，先保存其版本分支/提交，再由 SwarmIO gitlink 固定确切提交；不能只更新父仓库分支。
5. 重现必须使用 `git submodule update --init --recursive`；禁止用 `--remote` 拉取 BaM 最新代码替代发布 gitlink。
6. 同一版本使用全新的构建目录。已有 build 目录含源码副本，切换分支并不会自动更新该副本。
7. 复现时分别 checkout 发布提交并独立构建，不依赖最新分支中的脚本或补丁。已归档构建产物也必须与对应 manifest 一起保存。
8. 源码分支能独立构建，是在其记录的内核、NVIDIA、CUDA、IDXD 环境下成立，不保证兼容任意未来工具链。
9. 不在创建研究分支时推送、部署或切换服务器模块；这与后续服务器构建、验收是不同操作。

V0 与 V1 初始开发分支建立后，其余分支在满足依赖和验收条件后建立。既有 `swarmio_lab` 及其他实验分支保留。

## 4. V1：多 socket、多 GPU、多 DSA

### 4.1 已确认的实验拓扑

| 资源 | NUMA0 / socket0 | NUMA1 / socket1 |
|---|---|---|
| GPU | GPU0 | GPU1 |
| DSA | dsa0 | dsa2 |
| DSA PCI BDF | `0000:75:01.0` | `0000:f2:01.0` |
| 第一组逻辑 CPU | 0–19 | 20–39 |
| SMT 兄弟 | 40–59 | 60–79 |
| 候选服务 CPU | 8–15 | 28–35 |

CPU 集合仍需根据服务器占用确认。GPU 设备在运行记录中使用 UUID/BDF 固定身份，不依赖 CUDA 重编号后的 index。

### 4.2 最小实现范围

- 一个共享虚拟 NVMe 控制器/namespace，两个 GPU 拥有互不重叠的 QID 集合；管理队列初始化由唯一控制者负责，不能让两个进程独立 reset 同一控制器。
- 显式映射 `GPU → QP集合 → Service Unit → CPU/NUMA → DSA → group/WQ`。
- 两设备采用内部索引 0/1，实际设备编号为 0/2；不假设 DSA 编号连续。
- 默认每设备 4 个 service unit，总计 8 个 dispatcher、8 个 worker；沿用每单元一个 worker、独立描述符和队列完成所有权。
- 初始化、借用通道、失败回滚、卸载均支持多设备；SQ 获取及 payload 不回退 CPU 搬运。
- BaM/libnvm 提供按 QP/缓冲区选择 DMA peer 的映射；分别管理两个设备的映射生命周期和 pin 预算。
- 主机软件队列、描述符上下文优先本地放置；单独记录预留后端 RAM 的实际归属，不声称仅绑核就实现后端内存本地化。
- 增加每 GPU、每 DSA、每节点统计及统一测量窗口；区分各 GPU kernel 时间与双路共同测量区间，不能把不同时间窗口 IOPS 简单相加。
- 保留单 GPU、单 DSA 配置，作为 V0 与 V1 同参数回归入口。

### 4.3 对照与验收

- 先分别验证 GPU0+dsa0、GPU1+dsa2；然后双路同时验证 512B/4KiB 的内容与完成数。
- 若增加“不感知拓扑”的对照，和本地化版本共享合法多 peer 映射及正确性修复，只改变路由/放置策略。跨节点 P2P 不可用时记录为功能限制，不伪造吞吐样本。
- 单路、双路和拓扑对照固定可比较参数，分别报告总资源固定的实验和资源扩展实验。
- 每设备 SQ/payload 数量、字节数、BATCH 提交/回收均匹配；错误/超时为 0，停止后全部在途 DMA 排空。
- 单 DSA 原参数功能通过；性能用重复运行及分布比较，不规定尚无依据的提升幅度。
- 每个版本的服务器验收必须包含正常加载、测试退出、普通卸载及重复加载；本地替身测试不能替代此项。

## 5. V2：异步提交与完成通知

- 从 `release/v1-numa` 的已验收提交建立，保留 V1 拓扑组织。
- 保留同步接口；新增 `submit/test/wait` 与批量提交/回收。应用允许提交多个请求、执行其他工作，之后再消费完成。
- 每 QP 一个明确的 CQ 消费/回收者；CPU 或 GPU warp 轮询作为可选实现，分别评估，不同时推进同一 CQ head。
- 状态表按 `QP + slot/CID + generation` 识别请求，保存错误状态和生命周期。当前 CID 是 16 位空间，不能直接用 QD 大小数组按原 CID 索引。
- 只有确认 payload 完成且满足 GPU 数据可见性协议后才能发布完成状态；状态标志、CID、缓冲区均须安全回收。
- 分开比较队列放置位置、完成处理者、异步接口和真正计算/I/O重叠，避免一次改变多项无法归因。
- 首先复用/评估工作区已有 CoPilotIO 思路，不把已有异步方法作为全新算法；跨仓库代码需记录版本和许可证。
- 统一请求接口应支持 CPU 调用与 GPU 调用所需的后端选择；推理引擎适配代码在外部工程。
- 若为了应用需要扩展跨页请求，单列功能提交和测试，处理部分提交重试、子请求聚合、错误传播，不能仅移除 4KiB 限制。

验收覆盖乱序完成、环绕复用、队列满、错误、长期运行，以及同一状态槽多代复用。吞吐测试保持工作量、资源与模型参数一致，另报告 GPU 计算资源占用和重叠收益。

## 6. V3：可关闭的简单 FTL

- 从 `release/v2-async` 的已验收提交建立；阶段 3 的外部 KV offload 适配可同时进行，不作为 V3 开发分支的来源。
- 功能数据以 LBA 对应 RAM 保存，介质行为以 `LPN → PPA`、页/块状态、擦除次数独立建模；GC 不实际搬移逻辑 RAM 数据。
- 第一版实现页映射、覆盖写失效、空闲块分配、简单 victim 选择、GC 及统计；显式定义页/块几何与预留空间。
- 512B 部分页写必须定义读改写或写缓冲语义；GC 迁移、擦除和磨损均衡迁移占用模拟介质资源，回收生效时间不能早于模型允许时间。
- 统一 namespace 的映射和覆盖写语义必须跨 GPU/NUMA 一致；保护重叠读写，保持实际 payload 与映射状态一致。
- 保留 FTL off 模式，和 V2 同参数对照；FTL on 单独校准性能，不沿用简单模型的目标值宣称同等精度。
- 记录 host/NAND 写字节、GC/WL 迁移写、WAF、擦除分布、剩余 P/E 预算和 GC 引入的延迟；仅记录擦除次数不等于已实现磨损均衡。
- 时间寿命估计须说明耐久和写入速率假设，不将模型计数直接当成真实设备寿命。
- 数据初始装载、FTL有效占用建立、稳态写入预处理分别记录，正式计时前按规则排空与重置测量计数。

先用小几何逐事件验证正确性，再测大容量和高 IOPS。记录 FTL 本身的软件开销，避免它成为隐藏的仿真执行瓶颈。

## 7. 阶段 3/5/6 与框架的边界

应用工程单独固定：推理/检索系统提交、中间层提交、模型/索引校验值、缓存策略、数据布局和实验参数。与 SwarmIO 发布提交、BaM gitlink、构建 manifest 一起形成实验记录。

数据导入可来自真实 SSD，导入时间不计入负载时间；框架通用装载接口、缓冲区注册和请求拆分若需要新增，独立提交并注明所属版本，不让应用代码反向修改旧发布基线。

应用优先使用 V2；V3 可用后，对相同负载比较 FTL off/on。阶段 3 不必等待 FTL；研究 GC 和写放大时则必须使用能产生写入/失效的负载。

## 8. 统一实验记录

每轮至少保存：

1. SwarmIO 发布 tag/commit、是否有未提交改动、BaM gitlink/实际提交、配置及源码/产物校验值。
2. 构建 manifest；运行内核、NVIDIA、CUDA、IDXD、CPU/GPU/DSA 拓扑及 WQ 实际能力。
3. 请求数、请求大小、地址范围、分布、QP/QD、GPU线程、缓冲区、batch/depth、CPU和NUMA放置。
4. SSD模型参数、FTL模式与初始状态、预处理过程。
5. 初始化/预热/测量/排空边界、各路吞吐与合计吞吐、延迟分布及收集口径。
6. 正确性结果、错误/超时、提交完成平衡、在途资源和内核状态。
7. 应用版本、数据及缓存状态；CPU中转与GPU直达路径分别标明。

已有单 DSA 简单模型的 8 个调度实例、400ns 间隔对应约 20M 个 512B IOPS 的名义服务容量。V1 的“同一 SSD 模型比较”保持它不变；“最大执行吞吐”实验须明确调整模型容量或提供独立执行包络测试，不能把增加 SSD 模型容量计作拓扑优化收益。

每组计划至少 3 次有效重复，保留全部原始数据及失败记录。峰值、共同窗口平均、单 GPU kernel 平均、加载以来累计峰值分别报告，不混用。旧版本的独立重建与单路回归是发布验收的一部分。
